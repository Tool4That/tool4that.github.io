[B-00] Scenario brief and evidence first
  AREA: Investigation (forensics basics)
  GUI: open the scenario brief (the documented requirements for this machine) and write down authorized users, admins, required services, and anything forbidden
  $ sudo timeshift --create --comments "before hardening"   (practice VMs)
  WHY: Authorized users, admins, and required services decide what is a fix and
       what breaks the business. Evidence first: answer the investigation
       questions before any change (Defense Ladder f1).
  NOTE: Unfamiliar is distinct from unauthorized: trace it and ask before
        removing an agent (Defense Ladder s1). Keep a second terminal open as
        root (sudo -i) before touching PAM, sudoers, or SSH, so a typo leaves
        you a way back in. Timeshift ships with Mint: a snapshot before you
        start is a free undo on practice VMs. Right after the brief, start
        B-08's upgrade in a second terminal so it runs while you fix accounts,
        and read its result near the end; while it runs, other apt commands
        (B-05, B-09) wait for its lock, so work on the items without apt first.

[B-01] List human users, admins, and UID-0 accounts
  AREA: Account management (CIS Control 5)
  $ awk -F: '$3>=1000 && $3<65534 {print $1" uid="$3" shell="$7}' /etc/passwd
  $ awk -F: '$3==0 {print $1}' /etc/passwd
  $ getent group sudo admin adm wheel docker lxd disk
  $ awk -F: -v g="$(getent group sudo | cut -d: -f3)" '$4==g {print $1" has sudo as its primary group"}' /etc/passwd
  GUI: Menu, Administration, Users and Groups.
  WHY: An extra UID-0 user is a second root. sudo is the admin group (wheel on
       some distributions); docker, lxd, and disk are root-equivalent, since
       they can mount the host filesystem or read and write raw disks; adm reads
       logs. The default sudoers file also grants %admin, so a group named admin
       is a second admin path. An account whose primary group (field 4 of
       /etc/passwd) is sudo holds admin rights while staying out of the member
       list that getent group sudo prints.

[B-02] Remove or disable an unauthorized user
  AREA: Account management (CIS Control 5)
  $ id -u baduser                             (0 means a hidden root: skip the next two lines and follow the NOTE)
  $ sudo usermod -L -e 1 baduser; ps -o pid,unit,cmd -u baduser
  $ sudo loginctl disable-linger baduser; sudo loginctl terminate-user baduser; sudo pkill -KILL -u baduser; pgrep -u baduser
  $ sudo deluser --remove-home baduser
  $ sudo mkdir -p /root/removed-users && sudo deluser --remove-home --backup-to /root/removed-users baduser
  $ sudo userdel -r baduser
  $ sudo usermod -L -e 1 baduser && sudo usermod -s /usr/sbin/nologin baduser
  WHY: Deleting closes the login path; --remove-home removes planted files, and
       deluser also removes the user's crontab, which userdel leaves behind.
       --backup-to keeps a root-only copy of the home folder as evidence. Lock
       plus expiry plus nologin disables without destroying evidence: -e 1 also
       stops SSH key sign-in, which -L alone leaves working.
  NOTE: The brief decides between delete and disable. Lock first, end the
        processes, then delete: when pgrep -u prints nothing, the account is
        idle. A service that runs as the user restarts its processes until you
        stop the unit ps names (sudo systemctl disable --now <unit>). When id -u
        prints 0 the account is a hidden root: pkill -u on it ends every root
        process and deluser refuses it, so read its home (field 6 of getent
        passwd) and remove it with sudo userdel -f <name>, adding -r only when
        that home is its own.

[B-03] Fix admin group membership
  AREA: Account management (CIS Control 5)
  $ sudo gpasswd -d mallory sudo
  $ sudo loginctl terminate-user mallory      (ends the open sessions, which keep the old groups)
  $ sudo usermod -aG sudo alice
  $ groups alice
  GUI: Users and Groups: Account Type Standard or Administrator (Administrator =
       sudo group); the Groups row opens a tick list of every other group.
  WHY: Least privilege. -aG appends; -G alone replaces every group the user had.
       Open sessions keep the group list they started with, so a removed admin
       keeps sudo until each session ends, and a new member gains it at the next
       sign-in.

[B-04] Passwords: strong, forced change, no empties, root locked
  AREA: Account management (CIS Control 5)
  $ sudo passwd alice
  $ sudo chage -d 0 alice
  $ awk -F: '$3>=1000 && $3<65534 {print $1}' /etc/passwd | grep -vx "${SUDO_USER:-$USER}" | xargs -r -n1 sudo chage -d 0     (every human account except yours)
  $ sudo awk -F: '$2=="" {print $1" HAS NO PASSWORD"}' /etc/shadow
  $ awk -F: '$2!="x" {print $1" has something other than x in /etc/passwd field 2"}' /etc/passwd
  $ getent group nopasswdlogin; sudo gpasswd -d <user> nopasswdlogin
  $ sudo passwd -l root
  $ sudo passwd -S root                      (expect: root L)
  WHY: An empty shadow field means login with Enter. Locked root forces
       accountable sudo instead of a shared root password. pam_unix reads
       /etc/shadow only when field 2 of /etc/passwd is x, so an empty field
       there is also a login with Enter (sudo pwconv moves it back into
       /etc/shadow). Mint's login screen signs in every member of nopasswdlogin
       with no password at all; Users and Groups can place new accounts there,
       and passwd leaves that membership in place.
  NOTE: Record changed passwords somewhere safe (on paper, in a lab). Keep the
        password of the account you sign in with unless the brief says to change
        it. Leave service accounts and accounts that sign in only with keys out
        of the bulk chage line.

[B-05] Password aging and quality
  AREA: Account management (CIS Control 5)
  $ sudo sed -i 's/^PASS_MAX_DAYS.*/PASS_MAX_DAYS\t60/' /etc/login.defs
  $ sudo sed -i 's/^PASS_MIN_DAYS.*/PASS_MIN_DAYS\t1/' /etc/login.defs
  $ sudo sed -i 's/^PASS_WARN_AGE.*/PASS_WARN_AGE\t7/' /etc/login.defs
  $ sudo sed -i 's/^UMASK.*/UMASK\t\t027/' /etc/login.defs
  $ sudo chage -M 60 -m 1 -W 7 alice
  $ for u in $(awk -F: '$3>=1000 && $3<=60000 {print $1}' /etc/passwd); do sudo chage -M 60 -m 1 -W 7 "$u"; done
  $ sudo passwd -S -a                         (min, max, and warn for every account)
  $ sudo apt install -y libpam-pwquality
  $ sudo nano /etc/security/pwquality.conf
      minlen = 12  difok = 3  maxrepeat = 3  enforce_for_root
      dcredit = -1  ucredit = -1  lcredit = -1  ocredit = -1   (only when the brief's policy asks for character classes)
  $ sudo nano /etc/pam.d/common-password
      password  requisite  pam_pwquality.so retry=3        (ensure present)
      ... pam_unix.so ... remember=5                       (add to the pam_unix line)
  $ grep -n pam_pwquality /etc/pam.d/common-password
  $ sudo apt install -y libpwquality-tools && printf 'Summer2026\n' | pwscore
  WHY: login.defs only affects new users, so chage (or the loop) sets existing
       ones. UMASK sets the starting permissions of new files through pam_umask;
       with a private group per user (USERGROUPS_ENAB yes) users see 0007.
       pwquality enforces complexity when a password is changed; remember=
       blocks reuse. pwscore tests a password against the policy without
       changing one.
  NOTE: The scenario brief sets the numbers; these commands show one sample
        brief. The CIS Benchmark asks for a minlen of 14 or more, a history of
        24 or more, a maximum age of 365 days or fewer, a minimum age of 1 day
        or more, and a UMASK of 027 or stricter; Defense Ladder s2 compares the
        CIS and NIST rulebooks, and s3 applies them on Linux. Leave obscure in
        place. Numbers on the pam_pwquality.so line override pwquality.conf, so
        keep them in the conf file and leave the PAM line at retry=3. Install
        libpam-pwquality before any hand edit to a common-* file (B-06): after
        one, pam-auth-update stops updating those files while apt still reports
        success, so the grep is the proof. Open a root shell before the loop: an
        account whose last change is older than the new maximum must change its
        password at its next sign-in, yours included.

[B-06] Account lockout with pam_faillock
  AREA: Account management (CIS Control 5)
  $ sudo nano /etc/security/faillock.conf
      deny = 5   unlock_time = 1800   fail_interval = 900   audit
  $ sudo nano /etc/pam.d/common-auth          (order matters)
      auth  required                   pam_faillock.so preauth silent
      auth  [success=1 default=ignore] pam_unix.so            (existing line: set success=1, remove nullok)
      auth  [default=die]              pam_faillock.so authfail
      auth  sufficient                 pam_faillock.so authsucc
  $ sudo nano /etc/pam.d/common-account       (add first)
      account required pam_faillock.so
  $ sudo faillock --user alice
  $ sudo faillock --user alice --reset
  WHY: Stops online brute force. pam_faillock replaced pam_tally2, which current
       Ubuntu, Mint, and Debian releases have dropped. nullok allows empty
       passwords. faillock.conf holds the numbers; locking starts only once the
       PAM lines are in place, and numbers written on a PAM line override the
       file.
  NOTE: Test with su - alice in a second terminal before closing your root
        shell. Set the pam_unix line to [success=1 default=ignore] whatever
        number it had: some installs (Ubuntu desktop among them) ship
        [success=2] because a pam_sss line follows, and a 2 left in place sends
        every correct password past authsucc to pam_deny. unlock_time = 0 keeps
        a lock until sudo faillock --user NAME --reset or a reboot (the records
        live in /run/faillock); root stays exempt unless even_deny_root is set.
        Hand-added lines make pam-auth-update treat common-auth as locally
        modified; Hunter A-09 shows the managed route. On a desktop, the
        sufficient authsucc line ends the sign-in stack before pam_gnome_keyring
        runs, so the login keyring stays locked; the account line in
        common-account also resets the count, and A-09's managed route relies on
        it alone.

[B-07] Firewall with ufw
  AREA: Secure configuration (CIS Control 4)
  $ sudo apt install -y ufw
  $ sudo ufw default deny incoming
  $ sudo ufw default allow outgoing
  $ sudo ufw allow 22/tcp
  $ sudo ufw enable
  $ sudo ufw logging on
  $ sudo ufw status verbose
  GUI: Menu, Preferences, Firewall Configuration (gufw): Status On, Incoming
       Deny, Outgoing Allow.
  WHY: Default-deny inbound covers the service you have not found yet.
  NOTE: Only allow 22/tcp if the brief requires SSH. Add rules for required
        services (80/tcp, 443/tcp, 21/tcp).

[B-08] Updates: now and automatic (Update Manager)
  AREA: Patching (CIS Control 7)
  GUI: Update Manager (shield icon), Refresh, Select All, Install Updates
  GUI: Update Manager, Edit, Preferences, Automation: Apply updates automatically On, Remove obsolete kernels On; Other Updates: Update Flatpaks automatically On
  $ sudo mintupdate-cli upgrade -r -y --keep-configuration
  $ systemctl is-enabled mintupdate-automation-upgrade.timer; test -e /var/lib/linuxmint/mintupdate-automatic-upgrades-enabled && echo flag-on
  $ grep -qx -- '--keep-configuration' /etc/mintupdate-automatic-upgrades.conf 2>/dev/null || echo '--keep-configuration' | sudo tee -a /etc/mintupdate-automatic-upgrades.conf
  $ sudo apt update && sudo apt upgrade -y
  $ apt list --upgradable
  $ sudo flatpak update -y
  $ apt-mark showhold; cat /etc/mintupdate.blacklist 2>/dev/null
  WHY: Two separate goals: patched now, and configured to keep patching. Mint's
       automation runs only when both the timer and its flag file exist, and
       Flatpak apps update outside apt. -r refreshes the lists first, and
       --keep-configuration keeps your hardened configuration files when a
       package ships a new default (-y alone takes the package's version). Use
       Update Manager's automation rather than unattended-upgrades: on Mint its
       default origins carry the Mint name and codename, so they miss every
       Ubuntu security pocket (sudo unattended-upgrade --dry-run -d shows the
       Allowed origins). The daily job runs mintupdate-cli upgrade -r -y plus
       each line of /etc/mintupdate-automatic-upgrades.conf, so put
       --keep-configuration on its own line there too.
  NOTE: Start the upgrade first because it takes time. If Update Manager shows a
        broken mirror, fix Software Sources (I-11). A held package or a line in
        /etc/mintupdate.blacklist freezes that update: sudo apt-mark unhold
        <package>, and remove the line with sudoedit.

[B-09] Remove unapproved software
  AREA: Secure configuration: software (CIS Controls 2 and 4)
  $ apt list --installed 2>/dev/null | grep -Ei 'nmap|zenmap|john|hydra|medusa|wireshark|tshark|aircrack|ophcrack|netcat|ncat|socat|telnetd|nikto|metasploit|hashcat|sqlmap|doona|torrent|deluge|amule|scanmem|gameconqueror|minetest|aisleriot|mahjongg|sudoku|freeciv|wesnoth'
  $ dpkg-query -W -f='${db:Status-Abbrev}\t${binary:Package}\t${Section}\t${binary:Summary}\n' | awk -F'\t' '$1 ~ /^ii/' | grep -iE 'games|crack|brute|sniff|exploit|scanner|torrent|peer-to-peer'
  $ zgrep -hE '^(Start-Date|Commandline)' /var/log/apt/history.log*
  $ dpkg -l | grep -i <name>
  $ sudo apt purge --auto-remove nmap
  $ ls -la /usr/local/bin /usr/local/sbin /opt
  $ flatpak list
  $ flatpak uninstall -y <application-id>
  GUI: Software Manager (mintinstall), Installed
  WHY: Hacking tools, games, and P2P clients are acceptable-use violations and
       attack surface. The description search catches a tool by what it does
       when its name is unfamiliar, and the Section field lists every installed
       game in one pass. apt's history log shows what someone installed and
       when. Packages install outside /usr/local, so anything there was placed
       by hand.
  NOTE: Packages the brief requires (vsftpd, apache2, samba, openssh-server,
        mysql) stay; harden them in Watchman I-12. Mint blocks snapd with
        /etc/apt/preferences.d/nosnap.pref; that file is normal, not a finding.
        Flatpak apps hide from apt: list them separately. Expected stock hits to
        keep: cracklib-runtime and libcrack2 (the dictionary pam_pwquality uses)
        and the stock netcat-openbsd. Leave out -y and read apt's REMOVED list
        before answering Y, because --auto-remove also removes every package apt
        already marks as no longer required. apt stops at an unknown name, so
        purge only the names dpkg lists.

[B-10] Find unapproved media files
  AREA: Data protection (CIS Control 3)
  $ sudo find /home /root /tmp /var /dev/shm /srv /opt /mnt /media /usr/local -xdev -type f \( -iname '*.mp3' -o -iname '*.mp4' -o -iname '*.m4a' -o -iname '*.mov' -o -iname '*.avi' -o -iname '*.mkv' -o -iname '*.webm' -o -iname '*.wmv' -o -iname '*.flv' -o -iname '*.mpg' -o -iname '*.mpeg' -o -iname '*.wav' -o -iname '*.flac' -o -iname '*.ogg' -o -iname '*.aac' -o -iname '*.wma' \) -not -path '/var/lib/snapd/*' -not -path '/var/lib/flatpak/*' -printf '%u\t%s\t%p\n' 2>/dev/null
  $ sudo find /home /root /tmp /var/tmp /dev/shm /srv /opt -xdev -type f -size +32k -exec file --mime-type {} + 2>/dev/null | grep -E ': (audio|video)/'
  $ sudo sha256sum '<path>'; sudo rm -- '<reviewed path>'
  WHY: Many acceptable-use policies ban personal media on work machines, and the
       search also surfaces hidden folders in /home and /var/tmp. file reads
       each file's first bytes, so a song renamed to notes.txt still shows as
       audio/mpeg. -printf records owner, size, and path for the change log.
  NOTE: Confirm each path against the brief, then rm. Write the path down in
        case an investigation question needs it, and if a question asks for its
        hash, run sha256sum first (Defense Ladder s6). The OS ships its own
        sounds under /usr/share, so the search skips /usr except /usr/local; a
        hit inside an app folder (~/.local/share/flatpak, ~/snap, /opt/<app>)
        usually belongs to the app, so judge it against the brief, and images go
        only when the brief bans them. locate reads a nightly index that skips
        /tmp and /dev/shm, so find is the search to trust.

[B-11] Services: what runs, what listens
  AREA: Secure configuration (CIS Control 4)
  $ systemctl list-units --type=service --state=running
  $ sudo ss -tulpn
  $ systemctl list-sockets --no-pager
  $ sudo systemctl disable --now vsftpd
  $ sudo systemctl disable --now telnet.socket inetd xinetd 2>/dev/null
  WHY: Telnet and FTP are cleartext; avahi, cups, rpcbind, nfs and smb are
       exposure when nobody needs them. ss -tulpn shows the PID and program for
       every open port.
  NOTE: Required services stay. disable --now means stop it and do not start it
        at boot. Check what starts a service before you trust that: a systemd
        .socket unit can keep the port open after its .service is stopped (ss
        then shows systemd holding it). systemctl list-sockets shows each socket
        unit with the service it starts; disable the .socket as well as the
        .service. To trace an unknown listener to its unit and package, use
        I-07.

[B-12] Login Window: auto-login, guest sessions, screen lock
  AREA: Secure configuration (CIS Control 4)
  GUI: Menu, Administration, Login Window, Users: Guest sessions, Allow guest sessions Off; Automatic login, Username empty
  $ /usr/sbin/lightdm --show-config 2>&1 | grep -E 'allow-guest|autologin'
  $ sudo nano /etc/lightdm/lightdm.conf
      [Seat:*]   autologin-user=   allow-guest=false
  $ gsettings set org.cinnamon.desktop.screensaver lock-enabled true
  $ gsettings set org.cinnamon.desktop.screensaver lock-delay 0
  $ gsettings set org.cinnamon.desktop.session idle-delay 300
  GUI: Menu, Preferences, Screensaver: Lock the computer when put to sleep On, Delay before locking 0
  WHY: Auto-login or a guest session means physical access is root in ten
       seconds; an unlocked idle desktop is the same thing a few minutes later.
  NOTE: gsettings changes the current user only; check each authorized user or
        set it in the GUI for each. Guest sessions come from LightDM, so passwd
        -l guest reports an unknown user. /etc/lightdm/lightdm.conf is read last
        and overrides the drop-ins in lightdm.conf.d; --show-config prints the
        value in force and the file it came from. The Guest sessions section
        appears only when the guest-account tool is installed.

[B-13] Find plaintext credential files and unapproved archives
  AREA: Data protection (CIS Control 3)
  $ sudo grep -rIil --exclude-dir=.cache --exclude-dir=.mozilla --exclude-dir=snap --exclude-dir=flatpak -E 'passw(or)?d|credential|secret|api[_-]?key|BEGIN [A-Z ]*PRIVATE KEY' /home /root /tmp /var/tmp /dev/shm /srv /opt /var/www 2>/dev/null
  $ sudo find /home /root /tmp /var/tmp /dev/shm /srv /opt -xdev -type f \( -iname '*.zip' -o -iname '*.7z' -o -iname '*.rar' -o -iname '*.tar' -o -iname '*.tgz' -o -iname '*.tar.gz' -o -iname '*.tar.xz' -o -iname '*.txt' \) -printf '%u\t%TY-%Tm-%Td\t%p\n' 2>/dev/null
  $ sudo unzip -l '<file.zip>'; sudo python3 -m zipfile -l '<file.zip>'; sudo tar -tvf '<file.tar.gz>'
  $ file '<file>'
  WHY: A password list in a home folder hands an intruder every account it
       names, and an archive can carry tools past a package search. grep finds
       credentials by content, whatever the file is called; unzip -l, python3 -m
       zipfile -l, and tar -tvf list an archive without extracting it, and file
       names the real type of a renamed one.
  NOTE: The brief, the investigation questions, and required documents stay, so
        judge each path instead of deleting every .txt. Keys in ~/.ssh are
        expected for users the brief lets sign in with keys (I-01). Record the
        path and hash before removing anything (Defense Ladder s6). python3 -m
        zipfile works where unzip is absent.

[I-01] SSH hardening, only when SSH is required
  AREA: Access control (CIS Control 6)
  $ sudo grep -rniE '^[[:space:]]*(Include|Match|PermitRootLogin|PermitEmptyPasswords|PermitUserEnvironment|PasswordAuthentication|AllowUsers)' /etc/ssh/sshd_config /etc/ssh/sshd_config.d/
  $ sudo nano /etc/ssh/sshd_config.d/00-hardening.conf      (or the main file, after reading every drop-in)
      PermitRootLogin no        PermitEmptyPasswords no     MaxAuthTries 3
      LoginGraceTime 30         X11Forwarding no            UsePAM yes
      PermitUserEnvironment no
      PasswordAuthentication yes or no per the brief      AllowUsers alice bob
  $ sudo sshd -t && sudo systemctl restart ssh
  $ sudo sshd -T | grep -E '^(permitrootlogin|permitemptypasswords|permituserenvironment|maxauthtries|passwordauthentication|x11forwarding|allowusers) '
  $ sudo sshd -T -C user=root,host=localhost,addr=127.0.0.1 | grep -i '^permitrootlogin'
  $ systemctl list-units 'ssh*' --no-pager     (is ssh.socket the unit that listens on 22?)
  $ sudo systemctl daemon-reload && sudo systemctl restart ssh.socket   (after a Port or ListenAddress change)
  $ sudo find / -name authorized_keys -exec ls -l {} \; -exec cat {} \; 2>/dev/null
  WHY: Root over SSH means no accountability and the prime brute-force target. A
       planted authorized_keys file is a password-less backdoor that survives
       every password you fix. The && runs the restart only when sshd -t passes,
       so a config typo leaves the running server in place. Check how sshd is
       started: when ssh.socket owns port 22, a Port change or a disable aimed
       only at ssh.service leaves ssh.socket listening on the old port. sshd
       keeps the first value it reads, and the Include line at the top of
       sshd_config reads sshd_config.d/*.conf in name order, so one
       00-hardening.conf wins over the shipped drop-ins and the main file. sshd
       -T prints the values in force; -C applies any Match block, which plain -T
       skips.
  NOTE: Not required: sudo systemctl disable --now ssh.socket ssh.service &&
        sudo apt purge -y openssh-server, then confirm with sudo ss -tlpn that
        nothing holds port 22. Also read /etc/ssh/sshd_config.d/*.conf because
        Include files override. A drop-in whose name sorts before 00- still
        wins: the grep and sshd -T show it. If sshd -t or sshd -T stops at
        'Missing privilege separation directory: /run/sshd', run sudo mkdir -p
        /run/sshd and test again.

[I-02] sudoers audit
  AREA: Access control (CIS Control 6)
  $ sudo grep -R -nE 'NOPASSWD|!authenticate|ALL=\(ALL' /etc/sudoers /etc/sudoers.d/
  $ sudo visudo
  $ sudo visudo -f /etc/sudoers.d/<file>
  $ sudo -l -U mallory
  $ sudo visudo -c; sudo -k; sudo -v          (expect a password prompt)
  WHY: A NOPASSWD ALL line in a sudoers.d drop-in is a silent root backdoor.
       Never edit sudoers with nano: a syntax error means nobody can sudo.
       Defaults !authenticate, global or scoped as Defaults:<user>, acts like
       NOPASSWD on every rule it reaches; sudo -l -U lists it under Matching
       Defaults entries. Single quotes keep bash from reading the ! as history.

[I-03] Cron, at and systemd timers
  AREA: Malware defenses (CIS Control 10)
  $ cat /etc/crontab /etc/anacrontab 2>/dev/null; sudo ls -la /etc/cron.d /etc/cron.hourly /etc/cron.daily /etc/cron.weekly /etc/cron.monthly /var/spool/cron/crontabs
  $ sudo dpkg --verify cron cron-daemon-common
  $ dpkg -S /etc/cron.d/* /etc/cron.hourly/* /etc/cron.daily/* /etc/cron.weekly/* /etc/cron.monthly/* 2>&1 | grep 'no path found'
  $ for u in $(cut -d: -f1 /etc/passwd); do sudo crontab -l -u "$u" 2>/dev/null | sed "s/^/$u: /"; done
  $ systemctl list-timers --all
  $ sudo atq                                  (command not found means at is absent, along with any at jobs)
  $ sudo crontab -r -u baduser
  WHY: Cron re-creates users, re-opens ports, and re-installs tools every few
       minutes. It is the reason a fixed problem comes back. The stock
       /etc/crontab runs four run-parts jobs (hourly, daily, weekly, and
       monthly). dpkg --verify on cron-daemon-common, the package that owns
       /etc/crontab on 24.04, flags any edit (??5?????? c /etc/crontab) without
       a clean VM to compare against, and dpkg -S marks a hand-placed drop-in
       with 'no path found'.
  NOTE: Record and hash the program a planted job runs, end its process, find
        its other starters with I-07's grep -rlF line, then delete it. Cron
        rereads changed files every minute, so a fix needs no restart.

[I-04] Shell and startup persistence
  AREA: Malware defenses (CIS Control 10)
  $ grep -R -nE 'alias|nc |ncat|bash -i|/dev/tcp|curl .*\| *sh|wget .*\| *sh' /etc/profile /etc/bash.bashrc /etc/profile.d/ /home/*/.bashrc /home/*/.profile /root/.bashrc 2>/dev/null
  $ cat /etc/rc.local 2>/dev/null; ls -la /etc/init.d/ /etc/systemd/system/
  $ systemctl list-unit-files --state=enabled
  WHY: An alias on sudo or a reverse shell in .bashrc runs every time a terminal
       opens, including the one you use to fix things.

[I-05] Critical file permissions, world-writable, SUID
  AREA: Access control (CIS Control 6)
  $ sudo chown root:shadow /etc/shadow /etc/gshadow && sudo chmod 640 /etc/shadow /etc/gshadow
  $ sudo chown root:root /etc/passwd /etc/group && sudo chmod 644 /etc/passwd /etc/group
  $ sudo chown root:root /etc/sudoers && sudo chmod 440 /etc/sudoers
  $ sudo chown root:root /boot/grub/grub.cfg && sudo chmod 600 /boot/grub/grub.cfg
  $ sudo stat -c '%a %U:%G %n' /etc/passwd /etc/group /etc/shadow /etc/gshadow /etc/passwd- /etc/group- /etc/shadow- /etc/gshadow- /boot/grub/grub.cfg
  $ sudo chmod 750 /home/*
  $ sudo find / -xdev -type f -perm -0002 -not -path '/proc/*' 2>/dev/null
  $ sudo find / -xdev -type d -perm -0002 ! -perm -1000 2>/dev/null
  $ sudo find / -xdev -type f \( -perm -4000 -o -perm -2000 \) 2>/dev/null
  $ sudo chmod u-s /path/to/evil
  WHY: A readable /etc/shadow means offline cracking. A writable /etc/passwd
       means make yourself root. SUID on bash, nmap, find, or vim is instant
       root (see GTFOBins). The backup copies (names ending in -) hold the same
       data, so they take the same owner and mode as the main files. grub.cfg
       carries the kernel command line and any GRUB password hash; update-grub
       keeps the mode you set.
  NOTE: Common stock SUID files: passwd, su, sudo, mount, umount, chsh, chfn,
        gpasswd, newgrp, pkexec, fusermount3, ssh-keysign,
        dbus-daemon-launch-helper, and polkit-agent-helper-1. Stock SGID files
        include chage, expiry, unix_chkpwd, and crontab. Investigate anything
        else, and compare with a clean VM of the same release.

[I-07] Processes and connections: find the backdoor
  AREA: Malware defenses (CIS Control 10)
  $ ps -eo pid,ppid,user,cmd --sort=-%cpu | head -25
  $ ps -ef | grep -Ei 'nc |ncat|socat|bash -i|python.* -c|perl -e|xmrig|miner' | grep -v grep
  $ sudo ss -tulpn; sudo lsof -i -P -n | grep -Ei 'LISTEN|ESTABLISHED'
  $ sudo ls -l /proc/<pid>/exe; sudo cat /proc/<pid>/cmdline | tr '\0' ' '
  $ systemctl status <pid> --no-pager; dpkg -S "$(sudo readlink -f /proc/<pid>/exe)"
  $ sudo grep -rlF '<program>' /etc /var/spool/cron /home /root 2>/dev/null
  $ sudo kill -9 <pid>
  WHY: Killing a process is pointless unless you also remove what starts it:
       cron, a systemd unit, rc.local, .bashrc. Find the parent, then the file.
       systemctl status <pid> names the unit you disable, dpkg -S answers 'no
       path found' for a program no package installed (retry with /bin in place
       of /usr/bin first, since 24.04 merges them), and grep -rlF lists every
       file that starts the program.
  NOTE: When systemctl status names cron.service, rc-local.service,
        inetd.service, or a session scope, the process is that starter's child:
        remove the planted line, end the process, and keep the starter. A
        packaged python3, nc, or bash in /proc/<pid>/exe hides what it runs, so
        read cmdline. An exe path ending in (deleted) is a finding.

[I-08] AppArmor enforcing
  AREA: Secure configuration (CIS Control 4)
  $ sudo apt install -y apparmor-utils
  $ sudo systemctl enable --now apparmor
  $ sudo aa-status
  $ sudo aa-enforce /etc/apparmor.d/<profile>     (only profiles aa-status lists in complain mode)
  WHY: Mandatory access control: a compromised service cannot read files outside

  NOTE: Never run aa-enforce on /etc/apparmor.d/*: some shipped profiles are

[I-09] Logging and audit
  AREA: Audit logging (CIS Control 8)

      -w /etc/passwd -p wa -k identity
      -w /etc/shadow -p wa -k identity
      -w /etc/sudoers -p wa -k sudoers
      -w /etc/sudoers.d/ -p wa -k sudoers
  $ sudo augenrules --load && sudo auditctl -l
  $ sudo ausearch -k identity

  $ grep -oE 'audit=[^ ]+' /proc/cmdline        (after a reboot: audit=1)
  $ last; lastlog; sudo lastb | head; who; w

  WHY: Audit rules answer who changed /etc/passwd and when, which is exactly

       makes the kernel record from the first process, and an audit=0 anywhere

  NOTE: If rsyslog is not installed (journald only, as on a default Debian
        install), use journalctl.

[I-10] Account hygiene: shells, system accounts, odd groups
  AREA: Account management (CIS Control 5)
  $ grep -vE 'nologin|/bin/false|/bin/sync' /etc/passwd
  $ sudo usermod -s /usr/sbin/nologin <system-account>
  $ sudo chage -l alice
  $ getent group root shadow adm systemd-journal sudo admin docker lxd disk
  $ for g in shadow disk adm systemd-journal docker lxd; do awk -F: -v g="$(getent group "$g" | cut -d: -f3)" -v n="$g" 'g!="" && $4==g {print $1" has primary group "n}' /etc/passwd; done
  $ sudo gpasswd -d <user> shadow
  WHY: A service account with /bin/bash is a login. The disk group reads raw
       disks, which means the shadow file. Planted group memberships are quiet
       privilege. adm and systemd-journal read the whole system journal. An
       account whose primary group is shadow reads every password hash without
       appearing in the member list. gpasswd keeps /etc/group and /etc/gshadow
       in step, which a hand edit can split.

[I-12] Harden required services instead of removing them
  AREA: Secure configuration (CIS Control 4)
      vsftpd  /etc/vsftpd.conf: anonymous_enable=NO  local_enable=YES  write_enable=NO  chroot_local_user=YES  ssl_enable=YES
  $ sudo systemctl restart vsftpd && systemctl is-active vsftpd

      apache2 /etc/apache2/conf-enabled/security.conf: ServerTokens Prod  ServerSignature Off  TraceEnable Off ; apache2.conf <Directory /var/www/>: Options FollowSymLinks
  $ sudo apache2ctl configtest && sudo systemctl restart apache2
  $ curl -sI http://127.0.0.1/ | grep -i '^server:'; curl -si -X TRACE http://127.0.0.1/ | head -1
      nginx   /etc/nginx/nginx.conf http block: server_tokens off;  ssl_protocols TLSv1.2 TLSv1.3;
  $ sudo nginx -t && sudo systemctl reload nginx
      samba   /etc/samba/smb.conf [global]: map to guest = Never  restrict anonymous = 2 ; per share: guest ok = no

  WHY: Keeping the service running and making it safe is the real job, and real

  NOTE: vsftpd reads each line as option=value with no spaces around the = sign

        or -Indexes +FollowSymLinks. curl should print Server: Apache (or nginx)
        with no version, and TRACE should answer 405 (sudo apt install curl if
        it is missing).

[I-13] Browser protections (Firefox and Chromium)

        /etc/mintupdate.blacklist freezes them.

[A-01] Kernel and network hardening with sysctl
  AREA: Secure configuration (CIS Control 4)
  $ sudo nano /etc/sysctl.d/99-hardening.conf
      net.ipv4.ip_forward = 0
      net.ipv4.conf.all.accept_redirects = 0    net.ipv4.conf.default.accept_redirects = 0
      net.ipv4.conf.all.send_redirects = 0      net.ipv4.conf.default.send_redirects = 0
      net.ipv4.conf.all.accept_source_route = 0 net.ipv4.conf.default.accept_source_route = 0
      net.ipv4.conf.all.rp_filter = 1           net.ipv4.conf.default.rp_filter = 1
      net.ipv4.conf.all.log_martians = 1        net.ipv4.tcp_syncookies = 1
      net.ipv4.icmp_echo_ignore_broadcasts = 1  net.ipv4.icmp_ignore_bogus_error_responses = 1
      net.ipv6.conf.all.accept_redirects = 0    net.ipv6.conf.default.accept_redirects = 0
      net.ipv6.conf.all.accept_source_route = 0 net.ipv6.conf.default.accept_source_route = 0
      kernel.randomize_va_space = 2   kernel.kptr_restrict = 2   kernel.dmesg_restrict = 1   kernel.sysrq = 0
      fs.protected_hardlinks = 1   fs.protected_symlinks = 1   fs.suid_dumpable = 0
  $ sudo sysctl --system
  $ sysctl net.ipv4.ip_forward kernel.randomize_va_space
  $ sysctl -a 2>/dev/null | grep -E 'rp_filter|accept_redirects'      (an interface that still reads 2 keeps loose checking: sudo sysctl -w net.ipv4.conf.<iface>.rp_filter=1)
  $ sudo grep -rnE 'ip_forward|randomize_va_space|accept_redirects|rp_filter' /etc/sysctl.conf /etc/sysctl.d/ /etc/ufw/sysctl.conf 2>/dev/null
  WHY: ip_forward=1 turns the host into a pivot; syncookies and rp_filter blunt
       SYN floods and spoofing; ASLR at 2 and suid_dumpable 0 make exploitation
       harder. sysctl --system loads every file, including /etc/sysctl.d/;
       sysctl -p reads /etc/sysctl.conf alone. ip_forward goes first because
       changing it resets the interface settings, which would undo lines above
       it. The kernel applies the higher of the all value and each interface
       value for rp_filter, so the default line and the per-interface read-back
       both matter.
  NOTE: A bad change can leave ip_forward=1 or randomize_va_space=0 in
        /etc/sysctl.conf, a file in /etc/sysctl.d/, or /etc/ufw/sysctl.conf,
        which ufw applies each time it starts (its keys use slashes:
        net/ipv4/ip_forward). The stock ufw file sets log_martians=0, so with
        ufw on, change its two log_martians lines to 1 as well. On 24.04,
        /etc/sysctl.conf applies last and wins. Ubuntu and Mint ship rp_filter =
        2 (loose) in /etc/sysctl.d/10-network-security.conf; 1 is strict and can
        drop traffic on a machine with two network paths.

[A-02] Rootkits, tampered packages, malware
  AREA: Malware defenses (CIS Control 10)
  $ sudo apt install -y rkhunter chkrootkit debsums clamav
  $ sudo debsums -c; sudo debsums -ce
  $ sudo rkhunter --propupd && sudo rkhunter --check --sk
  $ sudo chkrootkit
  $ sudo systemctl stop clamav-freshclam; sudo freshclam; sudo systemctl start clamav-freshclam; sudo clamscan -r -i --log=/root/clamscan.log /home /tmp /var/tmp /opt
  $ clamscan --version                        (the signature date proves the database loaded)

       hardened system and reports every later change.
  NOTE: Signatures need internet. Run debsums first, then propupd, so rkhunter's
        baseline starts from checked files. clamscan loads about 1.2 GiB of

[A-03] The lsattr trap, core dumps, Ctrl-Alt-Del
  AREA: Secure configuration (CIS Control 4)
  $ sudo lsattr /etc/passwd /etc/shadow /etc/sudoers /etc/ssh/sshd_config
  $ sudo chattr -i /etc/passwd
  $ sudo nano /etc/security/limits.conf
      * hard core 0
  $ sudo systemctl mask ctrl-alt-del.target
  WHY: Attackers set the immutable flag so your useradd, passwd, and chage fail

       'Authentication token manipulation error', even as root. It is the most
       common reason a fix refuses to stick on a compromised machine.

[A-04] PAM deep dive
  AREA: Access control (CIS Control 6)
      required: must pass, keep going. requisite: must pass, stop on fail. sufficient: pass means done. optional.
  $ grep -nE 'nullok|pam_permit|pam_succeed_if' /etc/pam.d/common-auth /etc/pam.d/sudo /etc/pam.d/login /etc/pam.d/sshd
  $ sudo sed -i 's/ nullok//g' /etc/pam.d/common-auth
  $ grep -n 'pam_unix' /etc/pam.d/common-password
  $ sudo awk -F: '{h=$2; sub(/^!+/,"",h); if (h ~ /^[$](1|5|6)[$]/) print $1, substr(h,1,3)}' /etc/shadow
  WHY: An auth sufficient pam_permit.so line at the top of common-auth means any
       password works for everyone. Expect yescrypt (the Ubuntu and Mint
       default), obscure, and remember=5 on the pam_unix line, and leave the
       algorithm alone: adding sha512 there downgrades every new hash. A hash
       changes only when its password changes, so the awk line lists accounts
       still on MD5 ($1$), SHA-256 ($5$), or SHA-512 ($6$) to reset.

[A-05] Forensics toolkit
  AREA: Investigation (forensics basics)
  $ sudo find / -xdev -type f -newermt "2026-10-01" -not -path '/proc/*' -not -path '/sys/*' -not -path '/var/lib/*' 2>/dev/null | head -60
  $ sudo find / -xdev \( -nouser -o -nogroup \) 2>/dev/null
  $ sudo find / -xdev -uid <n> -ls 2>/dev/null; getent passwd <n>      (empty getent output: the owner was deleted)
  $ sudo find /home /root /tmp /var/tmp /dev/shm -name '.*' -type f 2>/dev/null
  $ sudo find /home /root /tmp /var/tmp /dev/shm /opt /srv /usr/local -xdev -type f -size -1024k -not -path '*/.mozilla/*' -not -path '*/snap/*' -not -path '*/.local/share/flatpak/*' -not -path '*/.var/app/*' -exec file {} + 2>/dev/null | grep -iE 'python|perl|shell script|ELF'
  $ comm -13 <(dpkg-query -L $(dpkg-query -W -f='${binary:Package} ') 2>/dev/null | sed -E 's#^/(s?bin)/#/usr/\1/#' | sort -u) <(sudo find /usr/bin /usr/sbin /usr/local/bin /usr/local/sbin -xdev -type f | sort -u)
  $ stat <file>; file <file>; strings <file> | head; md5sum <file>; sha1sum <file>; sha256sum <file>; sha512sum <file>
  $ sudo journalctl _COMM=sudo --no-pager | tail -40
  $ sudo grep -E 'useradd|userdel|usermod|groupadd|passwd' /var/log/auth.log* 2>/dev/null
  WHY: Investigation questions usually want a hash, a timestamp, a hidden path,
       or who ran what. -newermt finds what changed most recently. -uid takes a
       number, so it works after the account is gone. file reads first bytes, so
       a script or program needs no .py or .sh name to show up. comm lists
       programs in the system folders that no package installed; check each with
       dpkg -S before calling it planted, since a few come from install scripts.

[A-09] Lockout the managed way: pam-auth-update profiles
  AREA: Account management (CIS Control 5)
  $ ls /usr/share/pam-configs/; grep '^Module:' /var/lib/pam/auth
  $ sudo nano /usr/share/pam-configs/faillock
      Name: Enable pam_faillock to deny access
      Default: yes
      Priority: 0
      Auth-Type: Primary
      Auth:
        [default=die] pam_faillock.so authfail
  $ sudo nano /usr/share/pam-configs/faillock_notify
      Name: Notify of failed login attempts and reset count upon success
      Default: yes
      Priority: 1024
      Auth-Type: Primary
      Auth:
        requisite pam_faillock.so preauth
      Account-Type: Primary
      Account:

  $ sudo pam-auth-update --enable faillock faillock_notify
  $ grep -n pam_faillock /etc/pam.d/common-auth /etc/pam.d/common-account
  WHY: Ubuntu and Mint build common-auth and common-account from the profiles in
       /usr/share/pam-configs, and pam-auth-update computes every [success=N]
       jump for you, so the same two files work on both systems and survive
       later package installs. Priority sets the order: 1024 runs before
       pam_unix (256), and 0 runs after it. Indent each module line under its

        to /etc/pam.d/common-*, not updating.' and still exits 0, so always read
        common-auth back. Restore your backup first, or add --force, which keeps
        the old files as /etc/pam.d/common-*.pam-old and brings nullok back:
        strip it again (A-04) and move the .pam-old copies out of /etc/pam.d.
        Keep a root shell open and run the su - test from B-06. faillock.conf
        (B-06) still holds the numbers.

[A-10] Self-audit with Lynis
  AREA: Secure configuration (CIS Control 4)
  $ sudo apt install -y lynis
  $ sudo lynis audit system --quick
  $ sudo grep -E '^(warning|suggestion)' /var/log/lynis-report.dat
  $ sudo grep '^hardening_index=' /var/log/lynis-report.dat
  $ sudo lynis show details <TEST-ID>
  WHY: A second pair of eyes that changes nothing: Lynis reads the system and
       writes warnings, suggestions, and a hardening index from 0 to 100. Run it
       before and after your fixes, watch the index climb, and act on the
       suggestions the brief supports.
  NOTE: A suggestion is a lead to check, since some would break a service the
        brief requires. show details prints the log lines behind one test ID
        from the report.

------------------------------ FIX OR BREAK? (practice cards) ------------------
  Brief: Authorized administrators: alice. Authorized users: bob, carol.
  Action: Run sudo gpasswd -d bob sudo because bob is in the sudo group.
  Call: FIX. The brief lists bob as a standard user. Removing that account from
             sudo is least privilege.

  Brief: This server hosts the company website with Apache.
  Action: Run sudo apt purge apache2 to remove the web server.
  Call: BREAKS IT. Required service. Keep it running and harden it: ServerTokens
                   Prod, no directory listing, updates.

  Brief: Investigation 2: what is the SHA-256 hash of /home/bob/Music/track.mp3?
  Action: Delete all media files, then answer the investigation questions.
  Call: CHECK FIRST. Hash it first, then delete. Evidence before cleanup.

  Brief: Nothing in the brief mentions /opt/backup-agent.
  Action: Delete /opt/backup-agent because it is not a standard package.
  Call: CHECK FIRST. Unrecognized is distinct from unauthorized. Find what runs
                     it (a systemd unit, a cron job, the file owner) and ask the
                     system owner before removing a backup or monitoring agent.

  Brief: Only alice may log in with SSH; SSH must stay available.
  Action: Run sudo systemctl disable --now ssh.socket ssh.service.
  Call: BREAKS IT. SSH is required. Set PermitRootLogin no and AllowUsers alice,
                   and keep it running; ssh.socket is what listens on port 22,
                   so leave it enabled.

  Brief: No games are allowed on company machines.
  Action: Run sudo apt purge --auto-remove minetest after confirming no
          investigation question mentions it, and read the REMOVED list before
          answering Y.
  Call: FIX. Acceptable-use violation, and confirmed it is not evidence. Log the
             removal.

  Brief: The company uses Samba for the shared drive.
  Action: Set guest ok = no and map to guest = Never in smb.conf and restart
          smbd.
  Call: FIX. Hardening a required service without breaking it. Exactly the job.

  Brief: Standard users must not be able to run commands as root.
  Action: Delete the line '%sudo ALL=(ALL:ALL) ALL' from /etc/sudoers with nano.
  Call: BREAKS IT. That removes sudo for the real admins, and editing with nano
                   risks a syntax error that breaks sudo for everyone. Use
                   visudo and remove only the unauthorized entries.

  Brief: The machine must not forward traffic between its interfaces.
  Action: Set net.ipv4.ip_forward = 0 and run sudo sysctl --system.
  Call: FIX. Matches the brief and removes a pivot.

  Brief: Your useradd and passwd commands keep failing on this machine with
         confusing errors, even under sudo.
  Action: Reinstall the passwd package.
  Call: CHECK FIRST. Check sudo lsattr /etc/passwd /etc/shadow first. The
                     immutable flag is the usual cause, and a reinstall leaves
                     it in place.

  Brief: Timeshift is used for backups on this workstation.
  Action: Run sudo apt purge timeshift because backups are not a security
          control.
  Call: BREAKS IT. Required software per the brief. Leave it; snapshots are also
                   your own undo button.

  Brief: The design team installs approved apps through Flatpak.
  Action: Run sudo apt purge flatpak to remove an unneeded package manager.
  Call: BREAKS IT. Required tooling. Audit flatpak list for unapproved apps
                   instead.

  Brief: Lock an account after three failed sign-ins until an admin releases it.
  Action: Set deny = 3 and unlock_time = 0 in /etc/security/faillock.conf, then
          move on.
  Call: CHECK FIRST. faillock.conf only holds the numbers. Confirm the
                     pam_faillock lines are in common-auth (grep -n pam_faillock
                     /etc/pam.d/common-auth); locking starts only with them.

  Brief: Every account must need a password to sign in.
  Action: Set a password with sudo passwd for each account, then move on.
  Call: CHECK FIRST. On Mint, members of nopasswdlogin still sign in at the
                     login screen with no password, and passwd leaves that
                     membership in place. Run getent group nopasswdlogin and
                     remove each member with sudo gpasswd -d.

  Brief: Passwords must meet a quality policy.
  Action: Type password requisite pam_pwquality.so retry=3 into common-password
          by hand, then run sudo apt install -y libpam-pwquality.
  Call: CHECK FIRST. The hand-added line makes pam-auth-update treat
                     common-password as locally modified, so the package adds
                     nothing and apt still reports success. Install first, then
                     read it back with grep -n pam_pwquality
                     /etc/pam.d/common-password (B-05).

  Brief: Passwords must be at least 14 characters.
  Action: Set minlen = 14 in /etc/security/pwquality.conf while the
          pam_pwquality.so line still reads retry=3 minlen=8, then move on.
  Call: CHECK FIRST. Numbers on the pam_pwquality.so line override
                     pwquality.conf, so 8 still applies. Remove minlen=8 from
                     the PAM line and keep the number in the conf file (B-05).

------------------------------ SPOT THE FINDING (output snippets) --------------
  Lines from /etc/passwd. Tap the finding.
     root:x:0:0:root:/root:/bin/bash
     alice:x:1000:1000:Alice:/home/alice:/bin/bash
  >> sysadm:x:0:0::/home/sysadm:/bin/bash
     www-data:x:33:33:www-data:/var/www:/usr/sbin/nologin
  WHY: A second UID-0 account is a second root. Remove it (after noting it for
       the investigation).

  Output of getent group sudo. Brief: alice is the only admin. Tap the finding.
  >> sudo:x:27:alice,mallory
     adm:x:4:syslog,alice
     users:x:100:
     plugdev:x:46:alice
  WHY: mallory in the sudo group is an unauthorized admin: sudo gpasswd -d
       mallory sudo.

  Lines from /etc/shadow. Tap the finding.
     alice:$y$j9T$...:19600:0:99999:7:::
  >> bob::19600:0:99999:7:::
     carol:!:19600:0:99999:7:::
     daemon:*:19600:0:99999:7:::
  WHY: An empty second field means bob logs in with no password. ! and * mean
       locked, which is fine.

  More lines from /etc/passwd. Tap the finding.
     root:x:0:0:root:/root:/bin/bash
     alice:x:1000:1000:Alice:/home/alice:/bin/bash
  >> keola::1003:1003::/home/keola:/bin/bash
     syslog:x:104:110::/home/syslog:/usr/sbin/nologin
  WHY: An empty second field in /etc/passwd means keola signs in with no
       password, whatever /etc/shadow holds. Run sudo pwconv, then sudo passwd
       keola.

  Lines from /etc/ssh/sshd_config. Tap the finding.
     Port 22
  >> PermitRootLogin yes
     PasswordAuthentication yes
     X11Forwarding no
  WHY: PermitRootLogin yes lets attackers brute-force root directly. Set it to
       no and restart ssh.

  Lines found in /etc/sudoers.d/. Tap the finding.
     %sudo ALL=(ALL:ALL) ALL
     Defaults env_reset
  >> mallory ALL=(ALL) NOPASSWD: ALL
     root ALL=(ALL:ALL) ALL
  WHY: Passwordless full sudo for an unlisted user is a root backdoor. Remove it
       with visudo -f.

  Output of sudo ss -tulpn. Brief: no FTP on this machine. Tap the finding.
     tcp LISTEN 0 128 0.0.0.0:22   users:(("sshd",pid=655))
  >> tcp LISTEN 0 32  0.0.0.0:21   users:(("vsftpd",pid=812))
     udp UNCONN 0 0   127.0.0.53:53 users:(("systemd-resolve",pid=400))
     tcp LISTEN 0 128 127.0.0.1:631 users:(("cupsd",pid=701))
  WHY: vsftpd on port 21 when the brief forbids FTP: disable it and remove the
       package.

  Output of sudo lsattr. Tap the finding.
     --------------e------- /etc/shadow
  >> ----i---------e------- /etc/passwd
     --------------e------- /etc/sudoers
     --------------e------- /etc/group
  WHY: The i flag makes /etc/passwd immutable, so user changes fail with a
       misleading error. Clear it with sudo chattr -i /etc/passwd.

  Lines from /etc/sysctl.conf. Tap the finding.
     net.ipv4.tcp_syncookies = 1
  >> net.ipv4.ip_forward = 1
     kernel.randomize_va_space = 2
     fs.protected_symlinks = 1
  WHY: ip_forward=1 makes a workstation route traffic, a pivot for attackers.
       Set it to 0 and apply with sysctl --system.
