# Tool4That: notes for Claude

Static site published twice from this **public** repository: the primary at https://freeapp4that.store/ (Cloudflare Pages, deploys on push, honors `_headers` and `_redirects`) and the backup at https://tool4that.github.io/ (GitHub Pages). Never set a custom domain in GitHub Pages settings, or the backup address would redirect to the primary. Canonical addresses point at the primary.

## Layout
- `index.html` (the category chooser), `all/index.html`, one `<category>/index.html` per category, one `<series>/index.html` per series (`net-drills/`, `lockdown-drills/`, `lockdown-range/`), `404.html`, `robots.txt` (blocks the Internet Archive's crawlers, `ARCHIVE_BOTS` in `build_hub.py`; search engines stay allowed), `sitemap.xml`: **generated** by `build_hub.py` from `tools.json`. Don't hand-edit them; edit `tools.json` or the templates inside `build_hub.py`, then rebuild.
- `tools.json`: `categories` (slug, title, tagline, description, icon, note), `series` (slug, title, category, description, note: a named group of tools inside a category, with its own page), `sections` (slug, title, category, intro: an in-page grouping inside a category, one level *above* its series, with no page of its own, e.g. Learning and Practice under Cybersecurity), and `tools` (each with a `category` slug, an optional `series` slug, an optional `section` slug, optional `extras`: more download buttons, e.g. a reference `.txt` or a second `.html` download such as PFAT's offline edition, which gets its own `sha256` and `updated` and shows its own size and SHA-256 on the card, and optional `download_label` (the main download button's text, "Download .html" by default) and `download_note` (a short paragraph under the buttons that says what each download does), and `download_menu` (true: one Download menu, a script-free `<details>`, lists the main file and each `.html` extra with its size and SHA-256; Defense Ladder uses it for its one-grade downloads, built by `../tool4that-src-dlbackup/defense-ladder/build_downloads.py` and prepared with `prepare_tool.py --out <grade>.html`)). Category and series slugs and `all` are reserved folder names, so a tool slug can't reuse them. A series with no tools gets no page. **If a category defines any sections, every loose tool and every series in it must name a `section`** (a tool in a series inherits the series' section); `build_hub.py` refuses to build otherwise. A category with no sections renders exactly as before.
- `manifests/<group>.json` + `add_tools.py`: the standard way to prepare and register tools (see "Add or update tools").
- `concepts.json` + `build_concepts.py` + `design/study-map.html` + `design/command-atlas.html`: the data, checker, and page templates behind the Study Map (`study-map/`), a generated tool that maps every cybersecurity concept to where it is learned and practiced, and Command Atlas (`command-atlas/`), a generated tool that holds every command in the course (see "Study Map and Command Atlas").
- **Retired addresses simply 404.** The site is new, so the server forwards no old pages (no `_redirects`, no old-link aliases). The one forward lives inside a page: the Study Map sends an old `study-map/#cmd=<id>` link on to `command-atlas/#cmd=<id>`.
- `<slug>/index.html`: one self-contained tool per folder, built elsewhere (see "Tool sources").
- `.nojekyll`: GitHub serves the files exactly as committed.
- `.gitattributes` (`* -text`): byte-exact commits, so each tool card's SHA-256 matches the served file.

## Rules
- **Never edit a tool's `index.html` here.** Its inline scripts are pinned by SHA-256 in its Content Security Policy, so any edit breaks the page. Rebuild from source, then copy it in.
- **After adding or updating a tool,** run `py build_hub.py` (Windows) or `python3 build_hub.py`, then commit.
- **After adding, renaming, or rebuilding a cybersecurity tool,** rebuild the Study Map and Command Atlas too (see "Study Map and Command Atlas"): a tool's labels may have changed.
- **`build_hub.py`, `prepare_tool.py`, and `add_tools.py` read and write UTF-8 with LF explicitly.** Keep it that way, so runs on Windows don't rewrite files with Windows line endings or garble text.
- **Hub pages run no JavaScript** (`default-src 'none'`). Keep it that way.
- **No analytics, trackers, or third-party scripts.**
- **Never commit personal data:** LES files, screenshots, real pay figures, names, IDs. Everything here is public.
- **Commit identity:** user.name "Tool4That", with the GitHub noreply email.
- **Before pushing,** show `git status` and wait for approval. Never force-push.

## Add or update tools
1. **Put the source pages outside this repository**, e.g. `../tool4that-src-dlbackup/<group>/` for the cybersecurity tools or `../tool4that-src/<group>/` for the others (one self-contained HTML file per tool; a tool's reference `.txt` goes beside it). File names or page titles must match the tool's `match` patterns in its manifest.
2. **Describe the tools in a manifest** (`manifests/finance.json`, `manifests/learning.json`, `manifests/net-drills.json`, `manifests/lockdown-drills.json`, `manifests/lockdown-range.json`, `manifests/imagination.json`): slug, card text, badges, icons, `match` patterns, a `section` for tools outside any series (manifest-wide or per tool), and prep options (`strip_google_fonts`, exact-text `replace` pairs, `link_series_strip`, `allow_script`, `accept_runtime_fallback`, `frame_guard`, and, only for a tool that runs an engine in the browser, `allow_connect` (exact https prefixes it may fetch data from), `allow_wasm` (adds `'wasm-unsafe-eval'`: WebAssembly only, never JavaScript eval), `allow_worker_blob` (`worker-src blob:`), `allow_connect_data` (adds `data:` to connect-src so an engine can decode its own embedded WebAssembly; data: URLs never reach the network), and `allow_script_blob` (adds `blob:` to script-src, only for a page that runs code it decodes from its own embedded data, such as PFAT's offline edition or Chop Lab's audio engine, always with `pin_blocks`: the SHA-256 of each embedded file, passed as `prepare_tool.py --pin-block`, which reads the page the way a browser does and accepts it only when every data block is exactly `<script type="application/octet-stream" id="vendor-NAME">` and decodes to a pinned file, each pinned file and each `vendor-*` id appears exactly once, and every other element keeps clear of `vendor-*` ids and `octet-stream`)). Keep every allowance pinned to an exact versioned address. A tool can also carry `download_label`, `download_note`, and `variants`: a second download built from its own source page, each with `match` patterns, `out` (the file name inside the tool's folder), `label` (its button), `download_as`, and `prep` (merged over the tool's prep, so list every allowance the variant drops as an empty list). For a new series, add it to `series` in `tools.json` first.
3. **Prepare and register them in one step:**
   ```
   py add_tools.py manifests/<group>.json ..\tool4that-src\<group> --dry-run
   py add_tools.py manifests/<group>.json ..\tool4that-src\<group>
   ```
   `--dry-run` only shows which file matches which tool. The real run cleans each page (drops Google Fonts tags, applies the replacements, links the series strip), runs `prepare_tool.py` (hash-pinned CSP, canonical address, preview tags, icon, link back to the hub), copies the reference `.txt`, prepares each variant into `<slug>/<out>` (a variant's source page is matched first and set aside, so the tool's own `match` patterns see only the other pages), and adds or updates the `tools.json` entry, with each variant recorded as an extra. Tools whose source isn't in the folder are left as they are; `--only <slug>` limits the run to one tool. If `prepare_tool.py` refuses a page (e.g. inline `onclick=` handlers, outside requests), fix the **source** and re-run.
4. **Rebuild the hub** with `py build_hub.py`. It validates `tools.json` and computes the sizes and SHA-256s.
5. **Test it.** Serve the folder (`py -m http.server 8000`), open the hub, category, series, and tool pages, confirm they work, and check DevTools shows no console errors (policy violations appear there).
   - Manual alternative to steps 2-3 for a one-off: `py prepare_tool.py SOURCE.html <slug> --name "Name" --description "One or two sentences." --icon "🔢"`, then add the `tools.json` entry by hand (leave `sha256` and `updated` empty). `--out NAME` writes `<slug>/NAME` instead of `<slug>/index.html`, for a second download listed under the tool's `extras`.
6. **Publish.** Show `git status` and the diff, commit and push after approval, then check that the live page loads and its SHA-256 matches `tools.json`.
7. **Optionally redraw the hub preview image.** Edit `design/og-hub.html`, then render it at 1200×630, e.g. with headless Edge:
   ```
   & "${env:ProgramFiles(x86)}\Microsoft\Edge\Application\msedge.exe" --headless=new --screenshot="$PWD\og-image.png" --window-size=1200,630 "$PWD\design\og-hub.html"
   ```

## Study Map and Command Atlas
`study-map/` and `command-atlas/` are generated, never hand-built, by one build from the templates `design/study-map.html` and `design/command-atlas.html`.
- **Study Map** is the one place to find any concept: live search; tabs for Topic, Track, Grade, Layer (OSI and TCP/IP, plus the host), App, CLI, and My path; a concept list beside a detail pane on desktop, details in place on phones; and a full static listing for printing and for browsers without JavaScript. Each concept shows the Defense Ladder unit that teaches it, the drills and labs that practice it, and chips that open its commands in Command Atlas. The CLI tab is a light search box: one sentence, up to 12 command chips from a small name index, and a "Search Command Atlas for …" link. My path ratings read Explore, Revisit, and Strong on screen (the saved values stay `new`, `shaky`, and `solid`, under `t4t.study-map`). Served from the site or localhost, My path and each concept also show "Course quiz: X", the weakest answered quiz item for that concept, read (never written) from Defense Ladder's `defense-ladder-v1` save; a downloaded copy shows nothing there. It answers to `#c=<concept id>`, and an incoming `#cmd=<id>` forwards with `location.replace` to `../command-atlas/#cmd=<id>` (from disk, to the online Command Atlas).
- **Command Atlas** holds every command in the course on Windows, Linux, FreeBSD, and Cisco IOS: system pills, live search (commands, tasks, and the names of the concepts a command serves), options and arguments, every place it appears, the expected answers behind a reveal, vendor documentation, "Same job on other systems", "Concepts in the Study Map" chips (`../study-map/#c=<id>`), and a static listing of every command by system and category. It answers to `#cmd=<id>` and `#q=<text>` (typing writes `#q=`); Defense Ladder's "docs" links and the Study Map open it with `#cmd=`. Keep command ids stable. Its system choice is kept under `t4t.command-atlas.prefs`.
- **Cyber PUG lines** sit in their own section of a command, "Also in Cyber PUG (experimental)", after "Where it appears": each place carries the kind label "Checklist line · Cyber PUG (experimental)", the step's tab › phase › step, and the line, with the orange ⚠︎ "untested on a real system" unless Cyber PUG logs the line as run cleanly. Only the taught systems appear (Windows, the Debian family, FreeBSD, and Cisco); these places never count as uses or practice. The 17 concepts linked to commands show a matching "Also used in Cyber PUG (experimental)" line in the Study Map.
- **Cyber PUG-only commands** come from `..\tool4that-src-dlbackup\curriculum\cli\catalog-pug.json` (written by `build_catalog_pug.py` there: edit the script, then `py -I build_catalog_pug.py`): real commands of the taught systems that only Cyber PUG's lines use so far, each with a vendor link copied from Cyber PUG's citation registry or confirmed by hand. Command Atlas lists them as "Experimental entry" with "⚠︎ Cyber PUG" in place of a use count, shows only their Cyber PUG places, and never counts them as uses or practice.

Rebuild Defense Ladder and Cyber PUG here first when they changed: the build reads the published `defense-ladder/index.html` (unit titles and the quiz-to-concept map) and `cyber-pug/index.html` (tab, phase, and step titles), plus Cyber PUG's source `commands.json`, `command-fams.json`, and `tested.json` (`--pug`, by default `../tool4that-src/private/takeover-checklists/source`). It stops if a source step is missing from the page.
```
py build_concepts.py --strict
py ..\tool4that-src-dlbackup\curriculum\build_study_map.py --repo . --out ..\tool4that-src-dlbackup\learning
py add_tools.py manifests/learning.json ..\tool4that-src-dlbackup\learning
py build_hub.py
```
- The build writes `study-map.html` and `command-atlas.html` into `--out` (`--atlas-out` puts Command Atlas elsewhere). `py -I ..\tool4that-src-dlbackup\curriculum\cli\pug_lines.py --repo .` lists the Cyber PUG lines whose main command has no catalog entry.
- `build_concepts.py` checks `concepts.json` (the public concept data: layers, prerequisites, summaries, other names, references, and the places where each concept is learned or practiced) and confirms every place against the published tool pages here (`<slug>/index.html` plus its extras `.txt`): each `where` step and at least one `find` term must appear, case-insensitive, as whole words. It writes nothing. `--strict` exits with an error on any left-out place; `--links` requests every reference URL (needs internet).
- **A place was left out:** search that tool's page for the concept, then fix the place's `where` (the tool's own labels, joined with ` › `) or `find` (terms that must appear) in `concepts.json`. If the tool doesn't cover the concept, delete the place. Never add a place you haven't found in the tool. Concepts with no hands-on place are listed as gaps: candidates for new drills.
- `build_study_map.py` reads the private concept map in `..\tool4that-src-dlbackup\curriculum\` (`concepts.json`, `crosswalk.json`, `dl_units.json`, and the command catalog under `cli\`), uses only the places `build_concepts.py` confirms, fills both templates, and writes `..\tool4that-src-dlbackup\learning\study-map.html` and `command-atlas.html`. It refuses to write the pages if competition wording slips through (a Cyber PUG line that trips the check is left out of Command Atlas and listed in the build output), or if a `concepts.json` entry here isn't reached by any `crosswalk.json` entry (so nothing silently drops out). The curriculum folder never enters this repository.
- **Rebuild both whenever Defense Ladder's units, Cyber PUG, or any cybersecurity tool change.** Expect no `unit titles not found` line; if one appears, update the unit's exact title in `dl_units.json`.
- Defense Ladder answers to `#<grade>/<unit>` links (for example `#freshman/f7`), which the Study Map uses for exact-unit Learn links. Keep unit ids stable: never renumber one once published; a new unit takes the next free id in its grade.
- The templates' scripts can't contain the words the build refuses (for example `round` or `score` as whole words), because the check covers the whole page.
